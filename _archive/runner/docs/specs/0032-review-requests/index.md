## What you're agreeing to
- In a repo you list in your private PR settings with review requests on, a run checks every 10 minutes for PRs where someone asked you to review, and asks you on your phone: draft a review, or skip.
- "Draft a review" makes one model call that can only read: it runs the light `/code-review` over that PR's changes as plain text in an empty folder, never a copy of their project, so nothing in their PR can run on your machine. It cannot change the repo, push, or post anything.
- You get the draft on your phone (a file when it is long) and choose: post it as your review, edit it first (your text replaces the summary), or don't post.
- Only a tap on "post as my review" (or that exact reply) posts it; an approval is sent only when the draft itself says approve.
- Nothing about this goes into any repo; the switch lives only in your private settings file.

## Acceptance criteria
Today: `wf` reads PRs only through `pr.gh` and its allow list (`runner/pr.py:49`), polls PR records of watched repos in `pr.poll` at most every `POLL_GAP` (`runner/pr.py`, spec 0031 AC-1, AC-5), and a call always runs in the repo with write access (`runner/run.py` `Run.call`, `cwd=self.c.path`).

- **AC-1** (opt in): `~/.claude/private/pr.json`'s entry for the repo (`pr.private_config`) may carry `"review_requests": true` (the boolean only). Such a held repo is watched (spec 0031 AC-1) and its answered review questions are acted on in `pick()`. Nothing in a repo turns it on.
- **AC-2** (find requests): in `pr.poll` (so at most every 10 minutes during a run, and in the 0031 watch wait), for each such held repo `wf` runs `gh search prs --review-requested=@me --state open --repo <owner/name> --json number,title,author,url --limit 30`, then for each result not yet recorded `gh pr view <n> --repo <owner/name> --json number,title,author,url,state,isDraft,headRefOid,baseRefOid,additions,deletions,changedFiles`. Draft PRs and PRs by your own login are skipped. Each new one becomes a `reviews` record in `queue.json`: `{repo, number, feature: "review PR #<n>: <title, 60 chars>", title, author, url, head, base, size: [additions, deletions, files], state: "asked", draft: null}`. A failed read is one report line.
- **AC-3** (the question): case `review_request` (row P13): `review asked of you: PR #<n> <title> by <author>, +<a> -<d> in <f> files <url>`, options "draft a review" (recommended), "skip". "skip" sets `skipped`. A record whose PR closed, merged or no longer asks you (not in the search result) is set `gone` and its open question withdrawn.
- **AC-4** (the PR only as data, security review): on "draft a review", `wf` fetches `refs/pull/<n>/head` (`git fetch origin +refs/pull/<n>/head:refs/wf/review/<n>`, git hooks off) and drafts the head it got (recorded as the head). It never checks the PR out: it writes a clean folder `<run folder>/review-<n>/` holding only `pr.diff` (`git diff --no-ext-diff --no-textconv <base> <head>`) and `files.txt` (each changed file's text at the head, one after another, `--no-textconv`), so the PR's `.claude/`, `CLAUDE.md`, `.mcp.json` or hooks are never where claude loads configuration. The call runs with that folder as its working directory and `--setting-sources user`, `--strict-mcp-config` with no servers, `--tools Read,Grep,Glob`, and settings from the repo's guard with `disableAllHooks: true`, no `hooks`, the OS sandbox on with no network (`allowedDomains: []`), writes only in that folder, and the repo and its git dir in `denyWrite`; no credential reaches it (spec 0007).
- **AC-5** (the call): one call of kind `review_request` (not a box; box caps). The prompt starts with `/code-review PR #<n> (<base>...<head>)`, says the diff is between the data markers and in `pr.diff`, the full files in `files.txt`, to use Read, Grep and Glob only, never `/review`, `/review-stack` or `/code-review ultra`, to edit nothing, and to end with `DRAFT COMMENT: <file>:<line> <text>` lines, one `DRAFT SUMMARY: <one paragraph>` and one `DRAFT VERDICT: approve|comment|request changes`. The title, author and diff (cut at 150000 characters) are quoted as outside data between marker lines they cannot contain (`pr.fenced`, spec 0024's fence). `wf` keeps only those lines: comments whose `<file>` is a changed file and whose line is a number; a missing or other verdict becomes `comment`; a missing summary becomes "Review notes inline.". The draft is written to `<run folder>/review-<n>.md`.
- **AC-6** (the draft to you): the draft (verdict, summary, each comment as `<file name>:<line> <text>`, each line scrubbed and block list checked as phone text is today) goes to your phone before the question: on Telegram as up to 3 messages, longer as a `review-<n>.txt` file (`telegram.send_report`); on ntfy one message cut to the ntfy limit with `full draft in the run folder`. Then case `review_draft` (row P14): `post this review of PR #<n>? verdict: <verdict>, <k> line comments`, options "post as my review" (recommended), "edit first", "don't post".
- **AC-7** (edit): "edit first" asks case `review_edit` (row P15, no options): `reply with the text that replaces the summary`. Any reply, or any free text answer to `review_draft`, replaces the summary; the draft is sent again and `review_draft` asked again. Free text never posts.
- **AC-8** (post only on your tap): only the stored answer exactly `post as my review` posts. `wf` checks the PR is still open, runs the 0026 AC-6 scans over the summary and every comment (`check-msg` and attribution; a hit posts nothing and asks `review_draft` again naming what was found, so you edit first), writes `{commit_id: <head>, event, body, comments: [{path, line, side: "RIGHT", body}]}` to `<run folder>/review-<n>.json` and runs `gh api -X POST repos/<owner>/<name>/pulls/<n>/reviews --input <that file>`. `event` is `APPROVE` only when the drafted verdict is `approve`, `REQUEST_CHANGES` for `request changes`, else `COMMENT`. Success sets `posted` and adds a `review` entry to `run.json` `prs`; a failure asks `review_draft` again with the reason.
- **AC-8a** (security review, display equals action): the draft is stored as data (verdict, summary, comments with path and line), its SHA-256 (`reviews.digest`) recorded when it is shown and carried in the question; "post as my review" posts only when the stored draft still has that hash, and posts exactly that data. On Telegram the draft is shown exactly as it would be posted; ntfy shows a scrubbed, shortened view and says so. Post and edit count only as your strong answer (spec 0031 AC-14: Telegram, or a coded ntfy reply); otherwise nothing changes and the question comes back with the code form. The model is never run between showing and posting.
- **AC-8b** (security review, exfiltration): before it is stored or shown, every drafted line is dropped when it holds a token or key pattern, a local absolute or home path, a block list entry or a private name (`check-msg`); a comment must name a changed file and a line the diff shows; the summary falls back to the fixed text. The draft says how many lines were dropped. The call runs with `--restricted` (file tools confined to the data folder) and an environment holding only what claude needs to start.
- **AC-9** (allow list): `pr.allowed` adds exactly `search prs --review-requested=@me --state open --repo <o/r> --json <fields> --limit <n>` and, only with a `posting` flag that only `reviews.post` sets, `api -X POST repos/<o>/<r>/pulls/<n>/reviews --input <path in the run folder>`. `gh pr review` stays refused (it has no line comments).
- **AC-10** (never stop): rows P13 `review_request`, P14 `review_draft`, P15 `review_edit` join `PR_CASES` and `CASES`; no failure here ends a repo or the run.
- **AC-11** (words and architecture): `plain.PLAIN` rows for the three cases; `docs/architecture.md` invariant 1 (the one review post, only on your tap), invariant 3 (`/code-review` runs only inside this read only call, never `ultra`), invariant 4 (the three questions).
