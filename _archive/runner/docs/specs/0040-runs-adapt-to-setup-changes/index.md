## What you're agreeing to
- A run notices a phone channel you set up after it started: once Telegram is set up, its questions go there, and the ones already waiting are sent there again.
- A step stopped only because the run itself would not let it edit a file is started again by itself once a new setup lets it edit that file, and its question to you goes away.
- The design check looks only at the files your branch changed, even in a copy of the repo that holds only recent history.

## Acceptance criteria
Today: the channel is read once, at start (`runner/run.py:927`, `self.phone, self.ntfy = telegram.channel()`); a park is judged only by its section, its cap (`runner/run.py:1692` `applies`) and, at `wf` start, by commit, setup stamp or Claude version (`runner/run.py:719` `what_changed`, `runner/finish.py:912` `retakes`), and a park recorded before the first `swaps.jsonl` line has a null `setup`, so no swap ever takes it back; the design and `/test` base is `git merge-base HEAD main` (else `master`) and is null when that finds no common commit (`runner/run.py:3486` `test_base`), which makes every frontend file of the repo count (`runner/run.py:3515` `frontend_changed`).

- **AC-1** (phone channel): each time the run asks a question (before the question is queued) and each time it polls for replies, it compares `telegram.json`'s `(mtime, size, inode)`, or its absence, with what it saw when it last chose the channel (one `lstat`). On a change it calls `telegram.channel()` again. A file that loads as the channel in use only refreshes the config (a new token). A file that loads as the other channel: the run reads the old channel once more (a reply already sent there still answers its question), switches, resets the poll cursor and ping ids, logs `phone channel now Telegram, open questions sent again there` (or `ntfy`) once in `log.txt`, and sends every open question of its held repos again on the new channel, same id and body (the spec 0005 AC-14 re-ping). A file that does not load (refused, being written) keeps the channel in use and logs `phone channel kept: <reason>: <why>`; it is tried again when the file changes again. Design choice: re-send on the new channel instead of polling both channels for the rest of the run: one reader at a time keeps the cursor and ack logic as they are, and the one last read of the old channel covers a reply already on its way.
- **AC-2** (write deny park retaken): a `denied` or `blocked` Park record gains `denied_path` when its last call's permission denials name a file edit (`denied_path(data)`, spec 0021 F1) that the run's own guard denied at park time: the path, as written or resolved, is under the guard's `deny_paths` and no allow entry opens it (`opened`). Otherwise the field is absent and the park behaves as today. Wherever a run judges parks (`applies`, so at every pick: at its start and after each `setup <stamp> taken`, spec 0020 AC-5), a park with `denied_path` that the repo's current guard no longer denies no longer applies: the pick deletes it and its open case question (the existing `stale: <id> <feature>` line), logs `retaken <feature>: <path> no longer denied`, and the feature may run once more in this same run. With no guard built (`wf queue`), the park applies as today. Since spec 0033 AC-7 a call whose BLOCKED: comes from a recorded denied file edit parks `denied`, so in practice the field lands on `denied` parks; a `blocked` park whose call recorded no file edit denial (it only said the folder was locked) carries no path. Amended 2026-10-14 (your answer: fix it): such a park records `setups_seen`, the number of setups the run had taken, and gets one more try once a newer setup exists: in the same run, once the run took a setup after it parked; from an earlier run, once the newest swaps.jsonl stamp differs from the one it parked under. It logs `retaken <feature>: the setup changed`. Blocked again, it records the new count and is not tried again until the next setup.
- **AC-3** (base in a shallow clone): when `main` (else `master`) exists but `git merge-base HEAD <b>` finds no common commit, the base is the nearest merge base of HEAD with any other branch under `refs/heads` or `refs/remotes`, skipping HEAD's own branch, any remote branch of the same name, HEAD's upstream, every `*/HEAD`, and any branch that already contains HEAD (its merge base would be HEAD itself and hide committed work). Nearest is the fewest commits from the merge base to HEAD; on a tie, the first in `git for-each-ref` order. None found: no base, as today. With neither `main` nor `master`, nothing changes (every frontend file counts, spec 0010 AC-1). The same base serves `/test` (spec 0009 AC-9), since both read `test_base`.
