# 0030 · Autonomous mode: the session drives the runner

**Date**: 2026-10-13
**Status**: Accepted (built 376d029)
**Paths:** `runner/auto.py`, `runner/wf.py`, `runner/run.py`, `runner/tests/test_auto.py`, `live/skills/auto/SKILL.md`, `live/settings.json`, `AGENTS.md`
**Amends**: [0021](../0021-never-stop/index.md) (new run level row U11 `auto_off`), architecture invariant 5 (starting a run), [0020](../0020-one-command-wf/index.md) (who may run `wf -y`).

## What you're agreeing to
- You type `/auto on` in a Claude session. From then on that session starts `wf` itself whenever there is work, tells you its questions and the morning report, and starts it again when new work appears. You never open a terminal for it.
- It stays on through `/clear` and new sessions in that folder, until you type `/auto off`.
- The status bar shows `AUTO` and what the runner is doing. The bar cannot have a button (Claude Code only allows links there), so off is the `/auto off` command.
- `/auto off` lets a running build finish its current features and start no new ones; `/auto off now` stops it at once.
- Claude can never turn it on by itself.

## Acceptance criteria
- **AC-1** (state file): `<state>/auto.json` (`<state>` as spec 0011, `runner/run.py:496`), mode 0600, written through `ntfy.write` (`runner/ntfy.py:94`): `on` (bool), `folder` (real path of the folder it was turned on in), `since` (ISO time), `started` (the plan fingerprint of the last start, AC-5), `relayed` (question ids already told to you). One file: `on` in a second folder replaces `folder`, so only one session drives.
- **AC-2** (`/auto`): `skills/auto/SKILL.md` has `disable-model-invocation: true`, `argument-hint: on | off | off now`, and a body whose first line is `` !`wf auto $ARGUMENTS` `` (runs before Claude reads the skill), then one instruction: tell the user the printed line in one sentence. `wf auto on` writes AC-1 with the current folder and prints `autonomous: on in <folder name>`; `wf auto off` sets `on` false and prints `autonomous: off, a running build finishes its current features`; `wf auto off --now` (`/auto off now`) also runs `systemctl --user stop wf-auto` and prints `autonomous: off, build stopped`. Any other argument prints the usage and exits 2.
- **AC-3** (Claude never turns it on): `settings.json` `permissions.deny` gains `Bash(wf auto on:*)` and `Bash(*wf auto on*)`, and `wf auto on` refuses (exit 5, `refused: user_only`) when `WF_RUN` is set. Turning it off stays open to Claude: you may say "stop autonomous" in plain words and Claude runs `wf auto off`.
- **AC-4** (SessionStart, every source including `clear`): `wf auto hook` reads the hook JSON on stdin; when `hook_event_name` is `SessionStart`, `on` is true and the real path of `cwd` equals `folder`, it prints the driving instructions (below), the current AC-6 status line, and every open question not in `relayed`. Otherwise it prints nothing. It always exits 0 and swallows its own errors, as `wf report --hook` (`runner/report.py:353`). The driving instructions, printed as is:
  `Autonomous mode is on in this folder (the user turned it on with /auto on). You drive the wf runner: (1) when the status line says wf idle, run wf auto start; (2) then run wf auto wait with run_in_background and keep working or end your turn, never wait in chat; (3) when wf auto wait ends, act on its line: "question <id>" -> tell the user the question, its options and the recommended one, and say they answer on their phone; "run ended" -> run wf report and give its short list with the next command; "work" -> run wf auto start; "off" -> stop driving; then start wf auto wait again unless it said off; (4) never run wf auto on, never push or merge; (5) if wf auto start fails, say so once and do not retry until the user asks.`
- **AC-5** (`wf auto start`): refuses `off` (exit 5) when `on` is false, and does nothing but print `wf already running` (exit 0) when `systemctl --user is-active wf-auto` says active. Otherwise it runs `systemd-run --user --unit wf-auto --collect --working-directory <folder> --setenv PATH=<PATH> --setenv WF_AUTO=1 [--setenv XDG_STATE_HOME, XDG_CONFIG_HOME when set] -- <path of this wf> -y`, records the fingerprint of the plan bare `wf` would build (the `(repo, feature)` pairs with work, computed as `runner/finish.py:944` to `:948` do) in `started`, and prints `wf started` or `failed: <systemd-run error>` (exit 1). The unit lives outside the session, so `/clear`, closing the window or ending the session never stops it. `wf` already skips repos another run holds (spec 0020), and the fixed unit name stops a double start.
- **AC-6** (status line): `wf auto status` prints one line: `autonomous: on, wf <running N repos | idle>, <n> questions open` (N = held repo locks, counted as `runner/report.py:320` tests them; n = unanswered decisions in `queue.json`), or `autonomous: on in <folder name>` from any other folder, or `autonomous: off`.
- **AC-7** (every turn): on `UserPromptSubmit` in `folder` while on, `wf auto hook` prints the AC-6 line only. Elsewhere or off, nothing.
- **AC-8** (`wf auto wait`): checks every 30 s and exits 0 printing the first of: `off` (`on` turned false), `question <id>` (an unanswered decision not in `relayed`; the id is then added to `relayed`), `run ended` (the unit was active when the wait started and is not now), `work` (the unit is idle and the plan fingerprint is not empty and differs from `started`). It never exits for any other reason, so a run that ends with nothing new to do does not start again in a loop.
- **AC-9** (off finishes running work): a run started with `WF_AUTO=1` checks `auto.json` in `pick()` (`runner/run.py:1590`) before taking a new feature and in `end_wait()` (`:2326`) each poll; when `on` is false it ends with the new run level reason `auto_off`: no question, no new feature, the features already in progress were finished before `pick()` ran. `auto_off` joins `RUN_STOPS` (`runner/run.py:206`) and `CASES` as row U11 of spec 0021 ("Stays a stop: you turned autonomous mode off", no options), so spec 0021 AC-1's test stays green. An unreadable `auto.json` counts as on (a broken file never stops a night's build); the morning report is sent as for any stop (spec 0018 AC-1).
- **AC-10** (status bar): `settings.json` `statusLine` becomes `{"type": "command", "command": "/home/santiago/.local/bin/wf auto bar", "refreshInterval": 5}` (install.sh swaps the home path). `wf auto bar` passes its stdin to `bash ~/.claude/skills/jjstack/bin/statusline.sh` (2 s timeout), prints that output unchanged, and appends to its last line ` AUTO <running N repos, n question(s) | idle>` in green (ANSI 32) in the driving folder, or ` auto: <folder name>` uncolored in any other folder while on; nothing while off. jjstack's script is never edited (a jjstack update would overwrite it). A missing or failing jjstack script prints only the segment; `wf auto bar` always exits 0.
- **AC-11** (wiring): `settings.json` `hooks.SessionStart` and `hooks.UserPromptSubmit` each gain `/home/santiago/.local/bin/wf auto hook`. `AGENTS.md` Commands gains `wf auto on|off|status|start|wait|hook|bar`. `docs/architecture.md`: a component row for autonomous mode, and invariant 5 reads that a run started by `wf auto start` while you have autonomous mode on counts as started by you. Settings and skill reach `~/.claude` through spec 0019 live steps, never from a `wf run` call.
