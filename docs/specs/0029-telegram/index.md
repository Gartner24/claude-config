## What you're agreeing to
- The runner's questions and its morning report come to you in a Telegram chat with your own bot, instead of ntfy.
- You answer a question by tapping a button, or by replying to its message with your own words. Only your chat counts.
- The morning report can be long now: every item, not 12 lines. Very long reports come as a text file.
- The bot's secret key lives in one file outside the repo that only you can read; nothing ever prints it.
- Without that file, everything works through ntfy as today.

## Acceptance criteria
- **AC-1** (config): `<config>/wf/telegram.json` (`<config>` as spec 0005 AC-1) holds `token` (string matching `^\d{5,16}:[A-Za-z0-9_-]{30,64}$`), `chat_id` (integer), `aliases` (object of strings) and `block` (list of strings), the last two with spec 0005's meaning. `telegram.load()` raises `Invalid(why)` when the file is group or world readable or writable (`mode & 0o077`), is not a JSON object, or a field is missing or malformed. No `why` text, log line, warning, traceback or exception message ever contains the token: every error string from this module passes `redact()`, which replaces the token with `<token>` (the token sits in the request URL path, `https://api.telegram.org/bot<token>/<method>`). The file is written through `ntfy.write` (atomic, 0600 in a 0700 folder, `runner/ntfy.py:94`).
- **AC-2** (channel choice): `wf run` start check (today `ntfy.load()` at `runner/run.py:778`) picks the channel: `telegram.json` exists -> `telegram.load()`; an invalid file refuses `no_telegram` (exit 5, `refused: no_telegram: <why>`) and never falls back to ntfy, so a typo cannot silently send your questions to the old topic. No `telegram.json` -> `ntfy.load()` exactly as today (refuses `no_ntfy` when that is missing too, its `why` then naming both files: `no telegram.json or ntfy.json, run wf telegram init`). The one time code warning (`runner/run.py:781`) shows only for ntfy. The run keeps the chosen module as `self.phone` and its config as `self.ntfy` (name kept, fewer edits); every `ntfy.` call in `run.py` that sends, polls or parses (`:1357`, `:1358`, `:2217`, `:2256`, `:2278`, `:2297`, `:2315`) goes through `self.phone`. `ntfy.new_id`, `ntfy.boottime`, `ntfy.POLL_EVERY`, `ntfy.path` (allowed.json's folder, `:3043`) and `ntfy.write` stay as they are.
- **AC-3** (secret kept from calls): `telegram.json` is added to `CREDENTIAL_PATHS` (`runner/run.py:60`), so every call's sandbox `denyRead` (`:1049`), Read deny rules (`:1063`) and the app jail (`:73`) hide it. A test asserts a built call's settings deny reading it.
- **AC-4** (question message): `Topic.ping(d, stopped)` sends one `sendMessage` to `chat_id`: plain text (no `parse_mode`), body `<id>: <question>`, one `<n> <label>` line per option, then `tap a button, or reply to this message` (panel) or `reply to this message with your answer` (prose). Scrubbing is spec 0005 AC-7's (`ntfy.scrub`, block list, `option <n>` for an empty label, `question waiting, see terminal`), with larger cuts since a message holds 4096 characters: question 1000, body label 200, feature 40. A panel gets `reply_markup` `{"inline_keyboard": [[{"text": "<n> <label cut to 40>", "callback_data": "<id> <n>"}], ...]}`, one row per option, every option (not only 3). `d["sent"]` holds the body. Returns the sent `message_id` as a string. Same three tries 10 s apart, `None` when stopped, else `PingFailed(redacted error)` (spec 0005 AC-7), so spec 0021 U9 is unchanged.
- **AC-5** (other messages): `Topic.publish(message, priority, actions=None, stopped, title=None, tags)` keeps `ntfy.Topic.publish`'s signature (`runner/ntfy.py:231`): the title, when given, becomes the first line; priority 2 or lower (the acks) sends with `disable_notification: true`; `actions` and `tags` are ignored.
- **AC-6** (fetching, one reader): `telegram.fetch(cfg)` takes a non blocking `flock` on `<state>/telegram.lock` (`<state>` as spec 0011); when another process holds it, it returns at once. Holding it, it calls `getUpdates` with `offset` = the highest `update_id` in `<state>/telegram-updates.jsonl` plus 1, `timeout` 0 and `allowed_updates` `["message", "callback_query"]`, and appends one line per accepted update: `{"id": "u<update_id>", "time": <unix date>, "event": "message", "message": <text>}`. Only updates whose chat id and sender id both equal `chat_id` are kept; all others are dropped (offset still moves past them). The text is: a callback's `data`; a message replying to a bot message whose text starts `<id>:` -> `<id> <text>`; any other message as sent. Every callback query gets `answerCallbackQuery` (empty text) at once, so the button stops spinning. A plain message that neither matches `ntfy.REPLY` (`runner/ntfy.py:21`, 4 characters, a space, the rest) nor replies to a question gets one bot reply: `reply to a question message (swipe it), or start with its 4 letter id`. Lines older than 48 hours are dropped on each fetch. The log is 0600. Several runs side by side (spec 0017) never call `getUpdates` at the same time and never consume each other's updates.
- **AC-7** (polling): `Topic.poll(cursor)` calls `fetch`, then returns the log lines after `cursor` when it is `u<N>` (update id greater than N), else every line in the log. `run.py`'s poll (`:2243`) is unchanged except that it passes the whole message to `take` (`reader.take(text, ds, msg)`; `ntfy.Topic.take` gains the ignored argument). Polling stays every `POLL_EVERY` seconds in `SLICE` naps (`runner/ntfy.py:25`, `:26`), so Ctrl C still stops within a slice.
- **AC-8** (taking a reply): `telegram.Topic.take(text, ds, msg)` matches `ntfy.REPLY` (`<id> <rest>`) against an open decision whose `asked` time is not later than `msg["time"]` (a reply older than the question never answers it, even with a reused id). For a panel: `<n>` or `<n>,<m>` (with `multi`) or an exact label picks options as spec 0005 AC-8 forms 1 and 2; any other text is the free text answer (no one time code: only your chat is read, AC-6). For prose, the text is the answer. `source` is `phone`. The ack after an accepted answer (`runner/run.py:2296`) is unchanged.
- **AC-9** (morning report): with Telegram, the phone body is the AC-2 item lines of spec 0018 for every item (no 12 line or 1000 character cap, `runner/report.py:185`), scrubbed as spec 0018 AC-4 with question 300 and reason 80 cuts, still no park detail, path or run folder. A body up to 4096 characters is one message; up to 3 messages it is split at line boundaries; longer, the first message holds the head line, the `next:` line and `full report attached`, followed by `sendDocument` of the same scrubbed body as `wf-report.txt` (multipart built with the standard library). `sent` only when every message (and the file) returned a message id. ntfy keeps today's capped body.
- **AC-10** (`wf telegram init`): asks for the token with `getpass` (no echo, never on the command line, never in shell history), refuses a malformed one, calls `getMe` and prints `bot: @<username>`, calls `deleteWebhook` (getUpdates refuses while a webhook is set), then prints `open https://t.me/<username>?start=<code>` and `or send /start <code> to @<username>` where `<code>` is 6 characters from spec 0005's code alphabet. It long polls `getUpdates` (`timeout` 25) for up to 5 minutes and takes the first private chat message exactly `/start <code>`; its chat id becomes `chat_id`. `aliases` and `block` are copied from `ntfy.json` when it loads, else empty. It sends `wf connected` to the chat, writes the file, prints `saved <path>` (never the token) and exits 0; no matching `/start` in 5 minutes prints `no /start <code> received` and exits 6 with nothing written. An existing file is refused (exit 2) unless `--rotate`. `wf telegram test` sends one question (`yes`, `no`, feature `telegram test`), waits up to 5 minutes and prints `accepted: <answer>` (exit 0) or `no reply` (exit 6), as `wf ntfy test`.
- **AC-11** (standard library only): `runner/telegram.py` imports only the standard library (`urllib.request`, `json`, `fcntl`, `getpass`, `secrets`), plus `ntfy` and `wf`. Every HTTP call has a 10 s timeout beyond the long poll `timeout`.
- **AC-12** (docs): `AGENTS.md` gains `wf telegram init|test` in Commands and a Gotchas line (BotFather, the fallback rule). `docs/architecture.md`: the ntfy component row names both channels, the data flow line says `phone ping`, and invariant 4 adds the init `wf connected` message and the AC-6 hint reply.
