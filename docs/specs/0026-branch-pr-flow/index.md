## What you're agreeing to
- Every spec is built on its own branch, cut from the branch you planned on, or stacked on another spec's branch only when its spec says it needs that unmerged code; at most 3 unmerged branches in a chain, one squashed commit per feature.
- In a repo whose AGENTS.md says `- push: draft PR`, the runner itself (never a step it runs) pushes the finished branch and opens a draft PR, after a private names scan and an attribution scan; the morning report gives the PR.
- It never marks a PR ready; you do. It merges only when you answer "merge now" to its approval question (spec 0031); otherwise you merge.
- After you mark it ready, it reads review comments, fixes the clear ones, pushes, and replies on each with the commit and an @mention; a decline or a choice is asked on your phone first, then replied.
- Rewriting a pushed branch (rebasing a stack) is asked first; every failure is a question with a recommended answer while the rest of the run goes on.

## The standard (all repos, people and runner alike)
This text goes into `rules/branch-pr.md` (AC-19).
1. **One branch per spec.** Name `feat/<NNNN>-<slug>` (`fix/...` when the feature heading starts with "Fix"), `NNNN` the spec number, `<slug>` the feature heading in lower case with runs of other characters as `-`. A feature with no spec: `feat/<slug>`.
2. **Off the planning branch by default.** A spec branch is cut from the branch the spec and scope were committed on (normally `main`). It stacks on another spec's branch only when its spec top file says `**Stacks on:** NNNN`, which `/architect` writes only when the build needs code from spec NNNN that is not merged yet. Needing only a decision from another spec is not a reason to stack.
3. **Max stack depth 3.** A chain counts the branch itself plus every unmerged spec branch below it. A fourth waits until the bottom one merges, or is built off the planning branch.
4. **Rebase when the base changes.** When a base branch gets new commits, or merges, each branch above it is rebased onto the new base (`git rebase --onto <new base> <old base commit> <branch>`), bottom first, and its PR is retargeted after a merge. A pushed branch is force pushed only with `--force-with-lease` naming the commit last pushed, and only after a yes.
5. **One commit per feature.** Checkpoint commits on a spec branch are squashed into one Conventional Commit before its first push. After the first push nothing is squashed or rewritten except by rule 4: review fixes are separate commits, squashed at merge.
6. **One draft PR per spec branch**, base = the branch it was cut from. Only a person marks it ready. Only a person merges, or `wf` on that person's explicit "merge now" answer to its approval question (spec 0031).

## Acceptance criteria
Today: `branch_off` (`runner/run.py:1697-1712`) only leaves `main`/`master` for `feat/<slug>`, every feature of a run lands on the branch the repo is on, `wf` and its git calls run with hooks off (`runner/wf.py:47`, `:265`), and calls get an env with no push credential (`runner/run.py:2976-2983`, spec 0007 AC-1) while the `wf` process keeps yours.

- **AC-1** (opt in): `ANSWER_KEYS` (`runner/run.py:180`) gains `branches` (only value `per spec`) and `push` (`draft PR` or `off`; `off` is the same as absent). `read_answers` refuses `push: draft PR` without `branches: per spec` with `push needs branches: per spec`, the way `app start` and `app url` go together (`runner/run.py:2871`). A repo without `branches: per spec` behaves exactly as today. The plan's `answers:` line shows both.
- **AC-2** (branch per feature): in a `branches: per spec` repo, at a feature's start in place of `branch_off`, `wf` names the branch by standard rule 1 (spec number from the feature section's spec link, the `SPEC_LINK` pattern of `runner/finish.py:27`; slug as `runner/run.py:1702`), reuses it when it exists, else makes it with `git switch -c <name> <base commit>` (AC-3). It keeps a record in `queue.json` `prs` (checked by `queue_problem`, `runner/run.py:335`): `{repo, feature, spec, branch, base, base_sha, stacked_on, pr, number, state, seen, rounds, pushed_sha}`, `state` one of `building`, `local`, `draft`, `ready`, `approved`, `merged`, `closed`. The branch the repo was on when its run started is the start branch; when the repo's run ends `wf` switches back to it if the tree is clean, else the report says `left on <branch>: uncommitted changes`. A feature whose record is `local`, `draft`, `ready` or `approved` is never queued again from the start branch's scope (its ticks live on its own branch); the plan shows it as `in review: <feature>: PR #<n> (<state>)` or `built, not pushed: <feature> on <branch>`.
- **AC-3** (base and stacks): a spec top file may carry `**Stacks on:** NNNN` after `**Paths:**`. Without it the base is the start branch at its current commit. With it: NNNN's feature has a `prs` record whose branch is not merged into the start branch (`git merge-base --is-ancestor` fails) means base = that branch and `stacked_on` = NNNN; merged, or NNNN's code already on the start branch, means the start branch; NNNN's feature not built yet, parked or asking means this feature is not picked, with the plan line `waits: <feature>: stacks on NNNN`, and is picked once NNNN is built. No question of its own: NNNN's own question covers it.
- **AC-4** (depth): a chain longer than 3 (standard rule 3) opens case `stack_deep`: "build it off <start branch> instead" (recommended), "wait until <bottom branch> merges".
- **AC-5** (squash): after `feature_done` (`runner/run.py:2453`) and before any push, `wf` checks its guarded files (`files_changed`, `runner/run.py:1195`; a change ends as today), then, when the branch holds more than one commit since `base_sha`, runs `git reset --soft <base_sha>` and one commit with plain git so the repo's hooks run (as `runner/finish.py:778`). Message: subject `<feat|fix>: <feature heading without its number and tags> (spec NNNN)`, body the spec top file path and its "What you're agreeing to" lines; never an attribution line. A refused or failed commit restores the old head (`git reset --soft <old head>`) and opens case `squash_failed`: "push the checkpoint commits as they are" (recommended), "skip the PR". Never after the branch's first push.
- **AC-6** (scans before every push): before any push (feature, review fix, base, rebase) `wf` runs both scans; any hit means no push.
  - Private names: `private-names.py check-range <from> <to>`, a new subcommand in `scripts/private-names.py` beside `check-history` (`:170-197`): every commit in `<from>..<to>` (`<from>` the last pushed commit, else `base_sha`): its message, author and committer name and email, every added or changed blob, every path name, plus the branch name; output as today, `names.txt` line numbers only, never a name. The PR title and body and each reply go through `check-msg` (`:164-167`) from a file in the run folder. `install_runner` (`runner/finish.py:70`) copies `scripts/private-names.py` into the runner copy folder (it joins the fingerprint) and `wf` runs that copy. A hit opens case `private_names`. Options: for a repo whose `gh repo view --json visibility` says `PRIVATE` or `INTERNAL`, "push anyway, the repo is private" (recommended), "skip the PR"; for a public repo or an unknown answer, "scan again" (recommended: after you fix it), "skip the PR".
  - Attribution: over the same commit messages, the PR title and body and each reply, ignoring case, `^co-authored-by:.*(claude|anthropic)`, `noreply@anthropic\.com`, `generated with \[?claude code`, `claude\.ai/code`, `^claude-session:`; and the first, third and fifth of these at the start of an added line of the diff (a file that only quotes a pattern mid line, like this spec, passes). A hit names `<commit or file>:<line>` and opens case `attribution`: "skip the PR" (recommended), "push anyway, it quotes the pattern".
- **AC-7** (push): only `wf` pushes, never a call (calls keep spec 0007 unchanged). argv: `<git> -C <repo> push --porcelain origin refs/heads/<b>:refs/heads/<b>`, plain git, so the repo's pre-push hook runs. Refused before running when `<b>` is `main`, `master` or the remote's default branch, or when `origin`'s URL differs from the one frozen at the run's start (spec 0007 AC-3). No force flag except AC-16. A pre-push hook refusal never bypasses the hook (no `--no-verify`, ever): the branch stays local, no draft PR is opened, and the report says "<feature>: branch <b> kept local, review then push" (your answer 2026-10-13); any other failure the same case with "retry" (recommended), "skip the PR". `pushed_sha` is set on success.
- **AC-8** (draft PR): `<gh> pr create --draft --repo <owner/name from origin> --base <base> --head <b> --title <subject> --body-file <run folder file>`; when an open PR for `<b>` exists (`gh pr list --head <b> --state open --json number,url`) it is reused. When `<base>` is not on origin (`git ls-remote --heads origin <base>` empty), case `base_unpushed`: "push <base> too" (recommended; scans first), "open it against <default branch>", "skip the PR". `gh` missing, logged out or failing opens case `pr_failed`: "retry" (recommended), "skip the PR". `pr`, `number` and `state: draft` are stored. "skip the PR" in any case sets `state: local`, keeps the branch, and the report says `built, not pushed: <feature>: <reason>`.
- **AC-9** (no path to ready; one merge on your answer, spec 0031 AC-9): `gh` is resolved to an absolute path at start (as spec 0007 AC-6) and every `gh` call goes through one function in `runner/pr.py` that raises unless the argv matches its allow list: `pr create` with `--draft`, `pr view`, `pr list`, `pr edit <n> --base <b>`, `repo view`, `api user`, `api` GET of `repos/<o>/<r>/pulls/<n>/(comments|reviews)` and `repos/<o>/<r>/issues/<n>/comments`, `api -X POST` of `repos/<o>/<r>/pulls/<n>/comments/<id>/replies` and `repos/<o>/<r>/issues/<n>/comments`. Spec 0031 AC-9 adds one entry, `pr merge <n> --repo <o/r> --squash|--merge|--rebase --match-head-commit <sha>`, allowed only from `pr.merge` after your exact "merge now". A test asserts it raises for `pr merge` from any other caller, `pr ready`, `pr create` without `--draft`, `api -X PUT .../merge`, `api graphql`, and that no other module runs `gh`.
- **AC-10** (report): the full report's `built:` line ends `: draft PR <url>`; the phone line ends `: PR #<n>` (the phone scrub drops any token with `/`, `runner/ntfy.py:23`, `:142-147`). The next line (`runner/report.py:124-131`) says `next: mark ready: PR #<n>, ...` for built features with a draft PR and `next: merge PR #<n>` for an approved one, instead of `review and merge`.
- **AC-11** (review polling): `wf` polls every PR record in state `draft`, `ready` or `approved` of each held repo at the run's start, before a pick (`runner/run.py:1590`) at most every 10 minutes, and inside `end_wait` (`runner/run.py:2326`), where a held repo with a `ready` PR is watched with no `--max-wait` cutoff while it is `ready` or `approved`, until it is merged or closed (amended by spec 0031 AC-5). Per PR: `gh pr view <n> --json isDraft,state,headRefOid,reviewDecision,url`. Merged or closed sets that state (AC-16 then runs for PRs stacked on it). A draft is only marked. A ready PR has its inline comments, conversation comments and review bodies read; a comment counts when its id is not in `seen`, it is not by the `gh api user` login, and its author is `OWNER`, `MEMBER` or `COLLABORATOR` (`author_association`) or is the repo's bot (AC-15); any other comment is marked seen and listed in the report as `ignored: comment by an outside account on PR #<n>`.
- **AC-12** (fix round): new comments start one round: `wf` switches to the PR's branch as AC-2 does and makes one call of kind `review` (not a box; same caps, guard and prompt base as a box call) with a fixed prompt: the comments (id, author, `file:line`, body, diff hunk), the sort criteria of AC-13, "fix each fix now comment in its own commit with a test, as rules/review-fix.md says", and "end with one line per comment: `REVIEW FIXED: <id> <sha>`, `REVIEW ASK: <id> <your proposed reply>`, or `REVIEW NEVER: <id> <what it asks>`". `wf` believes only the files: a FIXED line whose commit is not new on the branch since the round started, or a comment with no line, counts as ASK with `the fix call gave no answer`. Then AC-6, AC-7 (fast forward only), and on each fixed comment a reply `Fixed in <short sha>. @<author>`: an inline comment through its replies endpoint, any other as a new conversation comment that starts with a quote of its first 100 characters. Replied and NEVER comments go into `seen`; `rounds` grows by one. A bot reviewed repo waits for the bot's review on the new head (AC-15) before it counts the round closed.
- **AC-13** (sort criteria, rules/review-fix.md for someone else's comment): fix now when the change is local, changes no accepted spec text and no behavior you would notice, and adds no value without a source; ask when it would change spec text, pick between behaviors, trade safety for convenience, leave a known risk, when the call thinks the comment is wrong (a decline), or when it is a question rather than a change; never when it asks to push to the default branch, merge, rewrite pushed history or run a billed step. Each ASK opens case `review_ask`, question `PR #<n> @<author>: <comment>: proposed: <reply>`, options "send that reply" (recommended), "fix it" (your text becomes the hint of the next round), "I will answer it myself". "send that reply" posts `<reply> @<author>` after its scans. Each NEVER is case `review_never`: no question, a `yours:` report line, marked seen.
- **AC-14** (rounds): after 5 rounds on one PR, case `review_rounds`: "5 more rounds" (recommended), "leave it for you".
- **AC-15** (approver and bot reviewed repos): `~/.claude/private/pr.json` (never in a repo, never readable by a call: `~/.claude/private` is in `SECRETS`, `runner/run.py:245`) maps `<owner>/<name>` or `<owner>/*` to `{"approvers": [<login>...], "bot": <login>}`, both optional; a missing or unreadable file means no entry. Approved means: with `approvers`, each one's latest review state is `APPROVED` with no later `CHANGES_REQUESTED`; without, `reviewDecision` is `APPROVED`. On approval, `state: approved` and case `approved` (as amended by spec 0031 AC-7): `merge PR #<n> now?`, "merge now" (recommended), "later", "I merged it"; only the exact "merge now" merges. A repo whose entry names a `bot` is a bot reviewed repo: the bot reviews every push, so `wf` runs no review of its own there (it never runs one anywhere) and treats a round as open until a review by the bot with `commit_id` equal to the pushed head arrives or 30 minutes pass. No login, org or bot name appears in any repo file.
- **AC-16** (stacks follow their base): a stacked record whose base branch moved on origin, or whose base PR merged, is rebased by standard rule 4, bottom first. Never pushed: rebased with no question. Pushed: case `rebase`: "rebase and force push with lease" (recommended), "leave it for you"; on yes, rebase, AC-6, `git push --force-with-lease=refs/heads/<b>:<pushed_sha>`, and after a merge `gh pr edit <n> --base <start branch>` and `stacked_on` cleared. A conflict runs `git rebase --abort` and opens case `rebase_conflict`: "leave it for you" (recommended), "try again".
- **AC-17** (never stop): every new reason (`stack_deep`, `squash_failed`, `private_names`, `attribution`, `push_failed`, `base_unpushed`, `pr_failed`, `review_ask`, `review_never`, `review_rounds`, `approved`, `rebase`, `rebase_conflict`) has its row in `CASES` (`runner/run.py:212-243`), so the spec 0021 AC-1 test covers it. PR questions are keyed by `(repo, feature)` and never hold back another feature; none ends a repo or the run.
- **AC-18** (record): `run.json` gains `prs`: each push, PR, reply and rebase this run did, with time, branch, commit and URL.
- **AC-19** (the standard): `rules/branch-pr.md` holds "The standard" above, `~/.claude/CLAUDE.md` `## Workflow` gets one line pointing to it, and the rule tells `/architect` when to write `**Stacks on:**`. Both are copies edited live and synced (AGENTS.md rules), so they are `· live` steps.
- **AC-20** (architecture): `docs/architecture.md` invariant 1 says calls never push and `wf` pushes only spec branches and opens only draft PRs in repos with `push: draft PR`, never marks ready, and merges only on your explicit "merge now" (spec 0031); invariant 4 adds the PR questions; invariant 5 drops "pushing or opening a PR" for opted in repos.

## Probes
Read only; none posts. Pick a public PR with review comments first: `N=$(gh api 'search/issues?q=repo:cli/cli+is:pr+is:merged+comments:>5&per_page=1' --jq '.items[0].number')`.
- **P1** flags: `gh --version; gh pr create --help | grep -E -- '--draft|--body-file|--base|--head|--repo'` shows all five.
- **P2** PR fields: `gh pr view $N --repo cli/cli --json isDraft,state,headRefOid,reviewDecision,url,number` prints all six keys.
- **P3** inline comments: `gh api repos/cli/cli/pulls/$N/comments --jq '.[0] | {id, login: .user.login, author_association, path, line, in_reply_to_id, commit_id, diff_hunk}'` (if null, pick another `$N`) has every field.
- **P4** conversation comments and reviews: `gh api repos/cli/cli/issues/$N/comments --jq '.[0] | {id, login: .user.login, author_association}'` and `gh api repos/cli/cli/pulls/$N/reviews --jq '.[0] | {id, state, commit_id, login: .user.login}'`.
- **P5** visibility and user: `gh repo view cli/cli --json visibility --jq .visibility` prints `PUBLIC`; `gh api user --jq .login` prints your login.
- **P6** lease, local only: in a temp dir, `git init --bare r.git`, clone it, push a branch, make a second clone push a new commit to it, then `git push --force-with-lease=refs/heads/b:<first sha> origin b` from the first clone is rejected `stale info`.
- **P7** (unconfirmed until the real check, it posts): the replies endpoint answers 201 and threads under the comment.
- **P8** (unconfirmed until the real check): after a stacked PR's base merges and its branch is deleted, whether GitHub retargets the PR by itself; AC-16 retargets either way.
