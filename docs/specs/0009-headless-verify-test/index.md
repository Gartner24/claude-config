## Summary

In a `wf run`, `/check verify` today has no browser and no app it can reach, so it reports BLOCKED. `/test` only looks at uncommitted files, so it misses work that was already committed. With this spec, `wf` starts your app itself, in its own jail (a `bwrap` sandbox that hides your keys and agent sockets but shares localhost). Verify and debug calls then get a throwaway headless Brave through the chrome-devtools MCP, and that browser can only reach your app. `/test` is told the feature's changes are everything on the branch since it left `main`.

## What you're agreeing to

- You add `app start` and `app url` to a repo's `## Standing answers` once. Without them, verify works as it does today.
- `wf` runs your app jailed during each verify and debug call: it cannot read your keys or reach your ssh or gpg agent, and can only write inside the repo (minus its settings and git hooks) and the caches.
- The browser is a fresh headless Brave with no cookies, it can only reach your app's local address, and it can only write files into the run folder. Fonts or scripts from the web do not load during verify. Its tool runs from wf's own download folder, never from `~/.npm`.
- `/test` covers every file changed on the branch since your local `main` (or `master`), so a branch holding several features tests them all.
- Build step 1 runs probes P2 to P7 before any other code; if any fails, the build stops and the spec goes back to /architect.
- After the review fixes (build steps 7 and 9), P2 to P11 run again through the built code before P8 and P9 count. A protected file that is a shortcut is locked at its real file, and a protected path the app creates while it runs stops the run.

## Threat model

Guarded: an accidental or prompt injected leak or push from the app or the browser that a run starts, whatever tool or spelling it reaches for first. Not guarded: a model actively working to escape (a `bwrap` or Chrome bug, a door not named here). The residual risks are listed once under Security model and accepted. There are no further hardening rounds on this feature; a new door found later goes to a new `/architect` run, not into the build. The review amendment of 2026-10-12 was that run (findings 1 to 7); it closes hardening again. Findings 8 (a probe failure through the built code) and 9 (a review of the step 7 commit) were settled the same day as one more amendment.

## Requirements

**User stories**:
- As you, I want an overnight `/check verify` to really drive my app in a browser, so that a Beta feature can pass verify without me, and only a login, captcha, 2FA or hardware stops it.
- As you, I want `/test` to see the whole feature even after checkpoint commits, so that it never asks "No changes" in the middle of the night.
- As you, I want the browser and the app a run starts to reach nothing of mine (keys, agent sockets, logged in sessions, other sites, my dotfiles), so that the push guard of spec 0007 still holds.

**Acceptance criteria**:
- **AC-1** (standing answer keys): spec 0006 AC-2 gains two keys. `app start`: the command that starts your app, any text (spaces allowed), kept exactly as written, never case folded. `app url`: `http://` or `https://`, host `localhost`, `127.0.0.1` or `[::1]`, an explicit port from 1 to 65535, an optional path, no whitespace, kept as written. The entry pattern becomes `^\s*[-*]\s+([^:]+?)\s*:\s*(\S.*?)\s*$`; `run suite` and `done` keep exactly their spec 0006 values and folding. A repeated app key refuses like any repeated key (spec 0006 AC-3). `wf run` refuses `bad_answers` (spec 0006 AC-3 path and detail form) when only one of the two keys is present (`app start and app url go together`) or when `app url` breaks the form above (`app url must be http(s)://localhost|127.0.0.1|[::1]:<port 1-65535>`). The `expected:` hint in the detail lists the two new keys. No app keys means no app and no browser for any call.
- **AC-2** (start checks): when the app keys are present, `start_checks()`, right after the standing answers check, resolves `npx` and `brave` with `shutil.which` then `os.path.realpath` (spec 0007 AC-6 style), then runs `<npx> -y <MCP_PACKAGE> --version` with `call_env()` plus `npm_config_cache=<MCP_CACHE>` (AC-4), a 120 s timeout, and the wf state dir as its working directory (never the repo or wf's own cwd: npx runs a matching package from the cwd's `node_modules`, P10). A missing binary, a non zero exit or a timeout refuses `no_browser` (exit 5, the `refuse()` path, no lock, no call), detail `npx`, `brave` or `mcp: <first stderr line>`. `bwrap` is already required by spec 0007 AC-8.
- **AC-3** (app jail): a browser call is a call of kind `debug`, or a box call whose command starts with `/check verify`, in a repo with the app keys. Before its first attempt, and again before each resume, `wf`:
  1. takes the spec 0008 AC-3 debug guard snapshot first, for a debug call (the app starts after it).
  2. requests `app url`. Any HTTP answer stops the run `app_port_busy`, detail `something already answers at <app url>` (a stop in spec 0008 AC-1, since every later feature would hit it too).
  3. starts `<bwrap> --die-with-parent --unshare-pid --ro-bind / / --dev /dev --proc /proc --tmpfs /tmp --tmpfs /run`. Then `--bind <p> <p>` for each existing path in: the repo, `~/.npm`, `~/.cache`, `~/.local/share/pnpm`, each at its `os.path.realpath` (a symlinked cache folder binds its target, no park). These are the write binds below. Then `--ro-bind <p> <p>` for each existing path in the calls' frozen `denyWrite` list (spec 0007 AC-2, the guard built at start: `deny_paths()` minus the common dir, plus the common dir's `config` and `hooks`), in that list's order, each bound at its `os.path.realpath` (source and destination), because `bwrap` refuses a destination that is a symlink and `~/.gitconfig` or `~/.zshrc` often is one (P2, finding 8). Each real path is bound once, at its first place in the list. An entry whose real path does not exist (absent, or a symlink pointing nowhere) is not bound and goes to the step 5 absent check instead. A symlink is itself read only under `--ro-bind / /` unless it lies inside a write bind, so `wf` parks `app_failed` before the app starts, detail `<path> is a symlink inside a writable folder`, with no `bwrap` run, when an entry has a symlink anywhere between a write bind and the entry: for a write bind `b` the entry lies lexically under (`b` itself or `b/...`), some prefix of the entry longer than `b` is a symlink (`os.path.islink`). Symlinks above the write bind (a repo reached through a symlinked `~/projects`) do not count. This check runs on every app start, a resume's restart included, after the debug snapshot (step 1) and before the port check (step 2). So the app is denied exactly what a call is denied: `<repo>/.claude`, git `config` and `hooks`, a linked worktree's `.git` pointer and its real path, `commondir`, `gitdir`, `config.worktree`, git include targets, hook token script folders, writable `PATH` folders. A writable `PATH` folder that is also a write bind (a pnpm `PNPM_HOME` at `~/.local/share/pnpm`) becomes read only for the app, the same limit calls have; an app that needs it parks `app_failed` with its log, accepted. Then `--tmpfs <d>` for each existing directory and `--ro-bind /dev/null <f>` for each existing file in `JAIL_HIDDEN`: `~/.ssh`, `~/.config/gh`, `~/.git-credentials`, `~/.netrc`, `~/.aws`, `~/.config/gcloud`, `~/.azure`, `~/.gnupg`, `~/.claude/.credentials.json`, `~/.config/BraveSoftware`, plus the wf folders, each resolved with `os.path.realpath` at start: the folder of `ntfy.path()`, the folder of `allowed.json` (both hidden when they differ), and `state_dir()` (run folders, locks, `MCP_CACHE`). The order is fixed: write binds, then the read only paths, then the hidden paths last; a read only path inside a hidden folder is covered by the hiding, fine. Then `--chdir <repo> /bin/sh -c <app start>`. It runs with `call_env()` (specs 0007, 0008, plus `WF_RUN`, AC-3 step 6) minus every `KEPT_ENV` name (`CLAUDE_CODE_OAUTH_TOKEN`), removed by exact name after `call_env()` returns, with `call_env()` itself unchanged, so the app holds no login; and with `start_new_session=True`, stdin `/dev/null`, stdout and stderr to `<run folder>/app-NN.log` (`NN` is the call's `seq`; a resume's restart appends `-rK`, K counting from 1). The network is shared, so the app is on your real localhost.
  4. polls `app url` (a GET, 2 s timeout) every 0.5 s. The first answer with a status below 500 means ready; a 5xx is polled again. If the process exits first, park `app_failed`, detail `app exited <code>: <tail>`. With no ready answer after `APP_READY` (120 s), park `app_failed`, detail `not ready at <app url> after 120 s (last status <n or none>): <tail>`. `<tail>` is the last 20 lines of the log through `clean()`, first 1000 characters. A park stops the app first. The readiness time counts toward the run's wall clock (`--max-hours`) but not toward the call's timeout (that clock starts after ready) or `--max-calls`.
  5. keeps the app through the call's retry (spec 0008 AC-6, same app, same log) and a usage limit wait. It stops the app when a decision wait starts (spec 0005), and restarts it through steps 2 to 4 before the resume. The app is stopped when the call is finished, after a park, and in `cleanup()` on every exit path. Right after every app stop, `wf` runs the spec 0007 AC-7 guarded file check (`files_changed()`) before any git command of its own: the call finished, a decision wait starting (before the question is sent), a park (including the step 4 `app_failed` paths), and `cleanup()` on every exit path including Ctrl C. That check also covers the frozen `denyWrite` paths that were absent at start. `freeze_guard()` records them in the guard as `absent_denied`, in list order: the `os.path.realpath` of each entry whose real path does not exist, kept only when it lies under the real path of a write bind (everything else is read only in the jail), and left out when it is already a `guarded_files` key. `files_changed()` checks `guarded_files` first, then `absent_denied`, so a path gives one detail. This runs wherever `files_changed()` runs: after every app stop, before every call, and in `cleanup()`, with or without an app. An `absent_denied` path that now exists (`os.path.lexists`) as anything but an empty regular file or an empty directory, neither a symlink, is a change, detail `<path> appeared during the run; inspect or delete it before opening a session in this repo`. The jail cannot bind an absent path, so a repo with no `.git/hooks` or no `.claude` used to let the app plant a hook that runs at your next commit (finding 9). The empty forms are Claude's sandbox placeholders, the same exemption `files_changed()` already gives an absent guarded file. A non empty directory at an absent path trips even when a call made it legitimately, accepted. `wf` creates nothing in the repo. `file_hash()` returns `directory` for a guarded file that has become a directory (it used to raise `IsADirectoryError`), so that is a change, not a crash. A moved file raises the `guard_changed` stop with the `files_changed()` detail; it wins over `app_failed` and any other park or stop reason already set, and a pending decision is never sent. A debug call's after snapshot (spec 0008 AC-3) is taken only after the app has stopped and that check passed (the check sits between the two).
  6. Stopping: `call_env()` carries `WF_RUN=<run id>` for every call and the app. On a stop, `wf` sends SIGTERM to the claude call's process group (when one is running) and the app's process group together, waits one shared `GRACE`, then sends SIGKILL to both. After every browser call and in `cleanup()`, it scans `/proc/*/environ` for processes of its own user carrying `WF_RUN=<run id>` (leftover Brave, the MCP's node process) and sends SIGKILL to each. `app_failed` is a park and `app_port_busy` a stop in spec 0008 AC-1.
- **AC-4** (browser MCP): a browser call and its retry and resumes get `--strict-mcp-config --mcp-config <MCP_BROWSER>` instead of spec 0007's empty `MCP_ALLOW`, and `--allowedTools` listing `mcp__chrome-devtools__<tool>` for every tool in `BROWSER_TOOLS` (the 1.10.1 tool list recorded in `verify.md` by P3, minus the AC-6 six). `MCP_BROWSER` is built at start: `{"mcpServers": {"chrome-devtools": {"type": "stdio", "command": <env path>, "args": ["-C", <wf state dir>, <npx path>, "-y", "chrome-devtools-mcp@1.10.1", "--isolated", "--headless", "--executablePath", <brave path>, "--proxyServer", "127.0.0.1:9", "--chromeArg=--webrtc-ip-handling-policy=disable_non_proxied_udp", "--chromeArg=--disable-quic", "--no-usage-statistics", "--no-performance-crux"], "env": {"npm_config_cache": <MCP_CACHE>}}}}`. `<env path>` is `env` resolved like `npx` (AC-2). `<wf state dir>` is the string `state_dir()` returns, unresolved, the same string the AC-5 check compares; it exists before the first MCP start because the `MCP_CACHE` creation below makes it. Claude Code starts the MCP in the repo, and npx would run a `chrome-devtools-mcp` planted in the repo's `node_modules` (P10), so `env -C` moves it to the wf state dir first. `MCP_CACHE` is `<wf state dir>/npm` (the spec 0004 state dir), a folder no call and no app may write, so `npx` never runs a package planted in `~/.npm`. `start_checks()`, before the AC-2 `--version` run, refuses `no_browser` (detail `state dir is writable by calls`) when the real path of `MCP_CACHE` lies under the repo, the git common dir or a `CACHE_DIRS` entry (an `XDG_STATE_HOME` pointing there), then creates it with `os.makedirs(exist_ok=True)`; the `--version` run fills it (the first run needs the npm registry). Two runs at once share it; npm's own cache locking covers that, accepted. Brave ignores the `--force-webrtc-ip-handling-policy` spelling (P5, 2026-10-12). Every other call keeps `MCP_ALLOW`. The version is pinned; raising it reruns P2 to P7 and changes this AC.
- **AC-5** (no attaching): the argv test reads the `MCP_BROWSER` args and fails unless `command` is the resolved `env`, the args start with `-C`, the wf state dir and the resolved `npx`, and they contain `--isolated`, `--headless`, `--proxyServer` and exactly one `chrome-devtools-mcp@<digits>.<digits>.<digits>` package, every `--chromeArg` is one of the two in AC-4, its `env` is exactly `{"npm_config_cache": <MCP_CACHE>}`, and none of `--browserUrl`, `--browser-url`, `-u`, `--wsEndpoint`, `--ws-endpoint`, `-w`, `--autoConnect`, `--auto-connect`, `--userDataDir`, `--user-data-dir`, `--channel`, or any `@latest` appears.
- **AC-6** (tool denies): a browser call's `--disallowedTools` adds `mcp__chrome-devtools__upload_file`, `mcp__chrome-devtools__take_heapsnapshot`, `mcp__chrome-devtools__performance_start_trace`, `mcp__chrome-devtools__performance_stop_trace`, `mcp__chrome-devtools__performance_analyze_insight`, `mcp__chrome-devtools__lighthouse_audit`.
- **AC-7** (browser hook): a browser call's inline `--settings` (spec 0007 AC-2) adds a second `PreToolUse` entry: matcher `mcp__chrome-devtools__.*`, `"type": "command"`, `"timeout": 10`, `"command": "<python3> -c '<BROWSER_GUARD>' <quoted app url> <quoted shots dir> || exit 2"`, where the shots dir is the `os.path.realpath` of `<run folder>/shots` (created by `wf` at start), with no trailing slash. `BROWSER_GUARD` is a constant in `runner/run.py` and fails closed. It exits 0 only when stdin parses as JSON, `tool_name` starts with `mcp__chrome-devtools__`, `tool_input` is an object, and all of these hold:
  - for `navigate_page` and `new_page`: either the tool is `navigate_page`, `url` is absent and `type` is `reload`, or `url` is a string with no `\`, no `@`, no whitespace and no character below U+0020 or equal to U+007F (checked before parsing: Chrome reads `\` as `/`, `urlsplit` does not), whose origin equals the `app url` origin. An origin is the lower cased scheme, the lower cased host, and the port (the scheme's default when none is given), from `urllib.parse.urlsplit`. `http://localhost:3000.evil.example`, `file://` and `chrome://` do not match. `navigate_page` with `type` `back` or `forward` (no `url`) is refused.
  - for any tool: every top level `tool_input` value whose key ends in `path` or `Path` (case kept, for example `filePath`, `requestFilePath`, `responseFilePath`) is a string that is absolute, already normalized (`os.path.normpath(v) == v`), equal to its own `os.path.realpath` (no symlink anywhere along it), and strictly inside the shots dir (it starts with the shots dir plus `/`; the shots dir itself is refused). A value that is not a string is refused. Checking the resolved path alone let a repo symlink be swapped between the check and the MCP's write.
  In every other case, any exception included, it prints `wf run: browser tool call refused` and the reason to stderr and exits 2.
- **AC-8** (prompt): a browser call's `--append-system-prompt` adds, after the spec 0006 text: ` wf started the app at <app url> and stops it after this step; do not start, stop or restart it. The confirm line and `run.json` `answers` show the two keys through spec 0006 AC-7, for example `answers: run suite yes, app start npm run dev, app url http://localhost:3000`.

## Decision

**Chosen option**: Option 1: `wf` starts the app in its own `bwrap` jail on the shared localhost, and only verify and debug calls get a locked down chrome-devtools MCP.

`/test` gets the branch base from `wf` in the prompt. Reasoning and options: see [rationale.md](rationale.md).

## Feature design

**Data model sketch** (no new storage):
- Standing answers (spec 0006): `app start` (text) and `app url` (local URL), both or neither, frozen at start.
- `Run`: `browser` (null, or `{"start", "url", "npx", "brave", "shots"}` resolved at start), `mcp_browser` (the AC-4 JSON string), the running app (`Popen` or null), `run_id` for `WF_RUN`.
- Call record: `app`, `test_base` (AC-10). Run folder: `app-NN[-rK].log`, `shots/`.

**State transitions** (one browser call):
`snapshot (debug only)` -> `check port` -> `starting` -> `ready` -> call (retry, limit wait) -> `stopped` -> `sweep`. A decision wait goes `stopped` -> wait -> `check port` -> `starting` -> `ready` -> resume. From `check port`, a busy port stops the run. From `starting`, a failure parks `app_failed` (the app is stopped first). Any run exit goes through `stopped` and `sweep` in `cleanup()`.

**API surface** (CLI and argv only):
| Surface | Inputs | Output | Errors |
|---|---|---|---|
| `wf run <repo>` start | standing answers, `PATH`, the npm registry | `answers:` part shows the app keys | `refused: bad_answers: ...` or `refused: no_browser: <npx, brave or mcp: ...>`, exit 5 |
| browser call | `app start`, `app url`, frozen guard | jailed app, logs, AC-4 MCP flags and allowed tools, AC-6 denies, AC-7 hook, AC-8 prompt | park `app_failed: <detail>`, stop `app_port_busy: <detail>` |
| `/test` call | `HEAD`, `main` or `master` | AC-9 prompt sentence, `test_base` | none (no base adds nothing) |
| `BROWSER_GUARD` hook | hook JSON on stdin, `app url` and shots dir as argv | exit 0, or exit 2 and the refusal on stderr | |

**Value sourcing**:
| Action | Value | Source |
|---|---|---|
| start | app command, app url | `## Standing answers` keys `app start`, `app url` (AC-1), frozen at start |
| start | `npx`, `brave`, `bwrap`, `python3` paths | `shutil.which` plus `realpath` (AC-2, spec 0007 AC-6) |
| start | MCP reachable | `<npx> -y <MCP_PACKAGE> --version` exit code, 120 s timeout |
| browser call | is it one | call kind `debug`, or box command starting with `/check verify`, and the app keys present |
| app jail | write binds | repo path plus `~/.npm`, `~/.cache`, `~/.local/share/pnpm` |
| app jail | read only over the binds | the calls' frozen `denyWrite` list (spec 0007 AC-2, built once at start) |
| app jail | hidden paths | `JAIL_HIDDEN`: spec 0007 AC-1 credential paths, spec 0008 AC-7 cloud paths, `~/.gnupg`, `~/.claude/.credentials.json`, `~/.config/BraveSoftware`; plus wf's config folder (`dirname(ntfy.path())`) and `state_dir()`; plus `/run` and `/tmp` as tmpfs |
| app jail | env | `call_env()` (specs 0007, 0008) plus `WF_RUN`, minus `KEPT_ENV` |
| app jail | log path | run folder, the call's `seq`, `-rK` per resume restart |
| readiness | ready or not | first answer below 500 at `app url`; `APP_READY` 120 s, poll 0.5 s, request timeout 2 s (constants) |
| `app_failed` | tail, last status | last 20 log lines through `clean()`, first 1000 characters; the last HTTP status seen or `none` |
| sweep | leftovers | `/proc/*/environ` holding `WF_RUN=<run id>`, owned by `wf`'s user |
| MCP | package version | `chrome-devtools-mcp@1.10.1`, pinned constant, read from npm on 2026-10-12 |

**Constants** (in `runner/run.py`): `MCP_PACKAGE = "chrome-devtools-mcp@1.10.1"`, `DEAD_PROXY = "127.0.0.1:9"`, `APP_READY = 120`, `MCP_CACHE` (a function of the state dir), `BROWSER_TOOLS`, `BROWSER_DENIED` (the AC-6 names), `BROWSER_GUARD`, `JAIL_HIDDEN`. The credential and cloud paths in `JAIL_HIDDEN` come from the one list specs 0007 and 0008 already use, not a copy.

**Key invariants**:
- No call reaches the app or the browser unless the repo's standing answers name the app. A call without a browser gets exactly what specs 0006 to 0008 give it.
- The app never runs outside the jail, never runs during a decision wait, never outlives its call, and never outlives the run.
- The browser never attaches to your running Brave, never keeps a profile, never loads anything but loopback addresses, and never writes outside the shots dir.
- After a run ends, no process carrying its `WF_RUN` is left.
- `wf` still writes nothing in a repo. The app may write in the repo outside `.claude` and git config and hooks, as the calls already do.

**Security model**: The app is repo code that unattended calls may have written, so it gets the same bar as a call. It sees no credential (env stripped including the Claude login token, key, token and real browser profile paths hidden, wf's config and state folders hidden, `/run` agent sockets gone), cannot write outside the repo and the caches, cannot write any path a call is denied (the frozen `denyWrite` list), any guarded file it changes is caught right after it stops, and it shares only the network. With nothing to log in with, it cannot push (spec 0007 threat model). The browser runs outside the Bash sandbox, so it is locked at four levels: a throwaway profile (no cookies or sessions), a dead proxy that only loopback skips with WebRTC UDP and QUIC off (no other host, IP literals included, whatever opened the request), the hook on every browser tool (navigation only to the app origin, file writes only into the shots dir), and tool denies (no local file uploads, no profiling dumps). The MCP itself runs outside every sandbox, so it runs from `MCP_CACHE`, which no call and no app can write (`wf` refuses to start when the state dir lies under a path calls may write, AC-4), and npx starts in the state dir, never the repo, so a planted `node_modules` is never picked (P10). Residual, accepted (see Threat model): the app, like a call (spec 0007 AC-2), can write `~/.npm`, `~/.cache` and `~/.local/share/pnpm`, so it could plant a package or cache entry that a later unsandboxed session of yours runs; the app can reach any host over the shared network (no credentials, same as spec 0007's IP literal residual); the browser can reach other services on your loopback (another dev server, a local database admin page) through app scripts, `evaluate_script`, a link or a redirect, since Chrome sends loopback past the proxy; the hook only limits the navigation tools to the app origin, and the AC-8 prompt says no more than that (finding 4); a download: P11 saw none saved by 1.10.1 headless, and if a later version saves one it lands in your default download folder, where Chrome never overwrites a file and nothing runs it (finding 6, rerun P11 on a version change); a file the app plants at an absent denied path and deletes again before it stops goes unseen, harmless since it is gone; a symlink swap on a denied path that existed at start is closed only by the step 3 symlink park (findings 8 and 9); a Chrome or `bwrap` escape.

## Consequences

**Positive**:
- A Beta feature with a web UI can close overnight: verify drives the real app instead of reporting BLOCKED.
- `/test` no longer depends on what is committed, so checkpoint commits (feature 14) cost nothing here.
- The guard of spec 0007 still holds: neither the app nor the browser gets a credential or an agent socket, and the browser reaches only loopback.

**Negative / tradeoffs**:
- Third party assets (web fonts, CDN scripts, payment widgets, analytics) fail to load during verify. A behaviour that depends on one reports FAIL or BLOCKED, so such a feature verifies by hand.
- An app that needs a database, Docker or a second service must have those running already, or `app start` must start them inside the jail. Otherwise it parks `app_failed`. An app that writes its own `.claude` or git hooks fails in the jail, or, when those were absent at start, stops the run `guard_changed`. A protected path that is a symlink inside the repo or a cache parks `app_failed`.
- Restarting the app per call and per resume costs its boot time each time.
- A leftover server of yours on the app port ends the whole run (`app_port_busy`).
- `/test` on a branch with several features, or with a stale local `main`, covers more than the feature (AC-9 accepted limit).
- `/check verify`'s before and after capture (refactors) can still only reach a second app copy from Bash, over HTTP, not through the browser.
- Bound to chrome-devtools-mcp 1.10.1 behaviour, its tool names and Brave's proxy handling. A version bump reruns the probes and updates `BROWSER_TOOLS`. Each run start needs the npm registry once (the `--version` check), or the cached package.

**Neutral**:
- Amends spec 0006 (AC-2 key table, entry pattern and case rule; AC-3 hint), spec 0007 (AC-4: verify and debug calls get `MCP_BROWSER`; AC-2 settings gain the browser hook on those calls), and spec 0008 (AC-1 park set gains `app_failed`, stop set gains `app_port_busy`; AC-3 snapshot order with the app). `/develop` notes each amendment in the step that builds it.
- Architecture page: the components table gains the app jail and the browser, invariant 8 gains the 120 s readiness bound and the leftover sweep, the threat model line covers the app and browser, and the skills table row for `/check verify` says it drives the app when the repo names one.
