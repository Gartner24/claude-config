## What you're agreeing to
- Before a night run, the `wf` screen guesses how much of your 5 hour window and your week the picked features will use, from what past runs used, and says "fits" or "does not fit, starts at <time>".
- A run that does not fit is never refused: by default it waits and starts right after the reset; you can type numbers to pick fewer features, or `now` to start anyway.
- To know where you stand, `wf` asks Anthropic for your usage the same way your status line does, with your login token, which it never prints, logs or saves.
- When a limit hits mid run, the run sleeps to the real reset time (your account says when), then goes on, as it already does.
- When the guess is unknown (no past runs yet, no answer from Anthropic), the screen says so and the run starts now.

## Acceptance criteria
- **AC-1** (read usage): `usage.read()` returns `{"five_hour": {"used", "resets_at"}, "seven_day": {"used", "resets_at"}}` (`used` a float 0 to 100, `resets_at` an aware datetime or None) or `(None, <reason>)`. It sends one `GET https://api.anthropic.com/api/oauth/usage` with the headers `jjstack/bin/statusline.sh:149-157` sends (`Authorization: Bearer <token>`, `anthropic-beta: oauth-2025-04-20`, `anthropic-version: 2023-06-01`, `Accept: application/json`, `User-Agent: claude-code/<run.claude_version()>`), timeout 5 s, with the token read from `<run.live_dir()>/.credentials.json` `claudeAiOauth.accessToken`. Reasons, fixed: `not a subscription login` (no such token, or `ANTHROPIC_API_KEY` set, or `ANTHROPIC_BASE_URL` set to a host other than `*.anthropic.com`), `usage service: <HTTP status or exception class name>`, `usage answer unreadable`. A null `utilization` reads as 0 with `resets_at` None. The token never appears in any output, `log.txt`, `run.json`, exception text, or file the runner writes: a test plants a known token, drives every path (success, HTTP 401, timeout, bad JSON) and greps stdout, stderr and the whole state folder for it, expecting zero hits.
- **AC-2** (cache and samples): a successful read is kept in `<state>/usage.json` (mode 0600) and reused for 60 s by any `wf` process; each new read appends `{"at", "five_hour", "five_hour_resets_at", "seven_day", "seven_day_resets_at"}` to `<state>/usage.jsonl` (mode 0600), kept to its newest 2000 lines. A `wf run` child reads usage at its start and after each call (so at most once a minute with the cache); a failed read is skipped silently in the run (one `warning:` line per run at most).
- **AC-3** (step estimates): `usage.estimates()` reads every `<state>/runs/*/run.json` (the newest 50, `RUNS_KEPT` at run.py:308) and groups call records by kind key: the box command's first word, or first two for `/check verify` (the allow list's key); kind `debug` is `/debug`, kind `sync` is `/sync` (spec 0008 AC-2). Calls with `limited` or `outage` true, or a null value, are left out of that value. Per key it keeps the median `cost_usd`, `duration_s` and token total (`usage_tokens` fields summed, run.py:3605-3614) and the sample count. A key with fewer than 3 samples uses the median over all calls of all keys; with no calls at all every estimate is None.
- **AC-4** (percent per dollar): `usage.ratios()` turns dollars into window percent from the samples: for each window (`five_hour`, `seven_day`), over consecutive `usage.jsonl` lines in the last 14 days with the same `resets_at`, it sums the rise in `used` and the `cost_usd` of every call record (all runs) that ended between the two lines (`started` plus `duration_s`), and the ratio is total rise over total dollars. Pairs with no call in between are skipped. Under 1 USD of matched calls gives None (unknown). Your own interactive use in the same hours makes the ratio higher, so the guess errs toward "does not fit" (accepted).
- **AC-5** (feature and run estimate): a picked feature's estimate is the sum, over its open boxes the runner would run (wf.py `Box.command`), of the key estimate, plus one `/sync`. The run's estimate is the sum over every picked feature in every repo (the repos share one account). Percent is dollars times the AC-4 ratio per window. Duration is the largest per repo sum (repos run side by side, spec 0017).
- **AC-6** (fit and start time): with usage read and every needed estimate and ratio known: week left = 100 minus `seven_day.used` minus a 10 point reserve kept for your own day use. The run fits the week when its week percent is at most week left. When it does not, the start time is `seven_day.resets_at` plus 2 minutes (`LIMIT_MARGIN`, run.py:300). When it fits the week but the 5 hour window has less left than the estimate of the first call of the first picked feature in any repo, the start time is `five_hour.resets_at` plus 2 minutes. Otherwise it starts now. A run larger than the 5 hour window fits: it sleeps through resets as spec 0021 U3 does.
- **AC-7** (the screen): `finish.cmd_wf` (finish.py:912) prints a `usage:` section after `build:` when there is a build: `now: 5h <used>% (resets <%a %H:%M>), week <used>% (resets <%a %H:%M>)`; `need: ~<p>% of a 5h window, ~<w>% of the week, ~<h>h (from <n> past calls)`; then one of `fits, starts now`, `does not fit the week: starts at <%a %H:%M>`, `5h window nearly used: starts at <%a %H:%M>`, or `unknown (<reason>), starts now`. Each numbered build line (spec 0020 AC-13) ends with ` ~<w>% week` when known. When the run does not fit, one more line names the largest prefix of the numbered list that fits now: `fits now: 1-<k>` (or `fits now: none`).
- **AC-8** (asks, never refuses): when the start time is not now, the prompt reads `Enter waits and starts at <time>, numbers to pick (1 2 4 or 1-3,5), now starts at once, anything else cancels: `. Enter keeps the start time; `now` starts at once; numbers pick (spec 0020 AC-13), then the usage lines are printed again for the pick and its start time is used with no second prompt. `-y` keeps the start time. `--only` picks before the fit is worked out. No usage outcome (unknown, does not fit, does not fit even a full week) refuses, skips a feature or changes the exit code; a test drives each outcome and asserts the builds start (now or at the time) and the exit code is the one spec 0020 gives.
- **AC-9** (the wait): report seen, the setup swap, the retakes and the checks run right after the confirm as today (spec 0020 AC-3 to AC-6, AC-8); only the builds wait. `run.parallel` (run.py:3684) takes a start time and, before its first child, prints `waiting for the usage reset: builds start at <%a %H:%M>, Ctrl C cancels` and sleeps in `POLL` slices until the wall clock passes it (a suspend does not shift it). Ctrl C during the wait starts no child, every repo shows `not started` in the summary, exit 130.
- **AC-10** (limit sleep uses the account): in `limit_wait` (run.py:2609), when `parse_reset` (run.py:3190) gives None, or gives a time earlier than the `resets_at` of a window whose `used` is 99 or more in a fresh `usage.read()`, the sleep runs to the latest such `resets_at` instead (the weekly limit text gives no date, so today a weekly limit sleeps 30 minutes and retries until the week resets). A failed read keeps today's rule (`LIMIT_UNKNOWN`, run.py:299).
