# When to switch on (beats skill text)

Source: docs/briefs/context-trim-and-all-chats.md Part 2, docs/briefs/retire-runner-features.md rows 10, 18, 20, 28, 31, 32, 38, 42, 44, 46, 59. Owner decision: a feature that used to run in some chats is a rule in every chat. It switches itself on when its condition is true; nothing is set per chat.

- App start and browser verify (10). When: the repo's `AGENTS.md` has `app start` and `app url`, and a `/check verify` runs. Do: start the app with `app start`, drive it at `app url` with the chrome-devtools MCP, then stop what you started. A repo without both lines: no browser verify.
- Keep awake (28). When: the owner says "I am leaving" or "finish it". Do: run `systemd-inhibit --what=sleep:handle-lid-switch --why=claude sleep 8h` in the background, so the lid can close.
- Parallel features (31). When: the owner says "do these features", or two or more features are ready. Do: run `/build-features`, never hand started agents. It starts one `isolation: worktree` agent per picked row, never two whose spec `**Paths:**` overlap (`spec-paths --overlap NNNN NNNN`), and proposes model and effort per row (effort at most high, at least low; haiku for lookup, sonnet for edits and review, opus for design and hard work). Never two apps on one port. Writing the scope rows and the `/architect` questions for all of them comes first (`rules/runner-handoff.md`; the build starts in a fresh chat per `rules/fresh-chat-after-architect.md`). Gates before each extra agent: see the 32 line below.
- Start gates (32). When: before each extra agent. Do: run `start-gates --running N` (N = agents already running). `go:` (exit 0) starts it and names the cores per suite; `wait:` (exit 1) starts nothing, unknown memory or 5 hour use included, and says why.
- Design check (18). When: `/sync` is about to close a feature in a repo with UI. Do: run `design-check` in the repo. Exit 1 (a changed frontend file without a passing, newer design-gate report) or exit 2 (git failed) refuses the close: show its lines to the owner.
- Scope marker warnings (59). When: `/scope` or `/sync` has written a scope. Do: run `python3 ~/.claude/skills/chip-dash/plan.py --warnings <repo>` and show every line it prints (exit 1) to the owner.
- Issue reread (20). When: `/develop` or `/check verify` runs on a row whose `Source:` is a GitHub issue. Do: run `issue-reread <issue> --spec <spec top file>`. Exit 1 (the issue changed after the spec): show the lines and ask the owner before building. Exit 2 (not read): tell the owner it was not read and why.
- Review isolated (46). When: the owner asks to review someone else's PR. Do: run `review-isolated <pr>`; it drafts the review in a locked down claude and prints the draft path and verdict. Post it with `gh pr review` only on the owner's exact yes.
- Self-merge checklist (38). When: your own or a personal repo only, never a work or client repo, and you are about to merge a PR. Do: merge only when the scope's verify and test boxes are ticked, the repo's own suite passes on the PR head, and all checks are green for that head (a PR with no checks yet: wait 10 minutes for a first one). Merge with `gh pr merge --squash --match-head-commit <sha> --delete-branch`, one PR at a time.
- Review comment loop (42). When: a PR you opened has open review comments. Do: `/loop 10m` with `sentry-skills:iterate-pr`. Fix clear comments one commit each, reply with the sha, ask the owner before declining one, stop after 3 rounds. Sorting of findings stays in `rules/review-fix.md`.
- Foreign change check (44). When: the branch has commits by someone else. Do: list the changed files that can run code - `.claude/`, `CLAUDE.md`, hook managers, package scripts, build and test config - and ask the owner before running tests or hooks there. For claude on that code use `--setting-sources user --strict-mcp-config`.
